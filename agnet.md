# Agent work boundaries

- Public release: preserve the remote repository's existing commits, publish a sanitized current source snapshot and explicit release assets, and never include local `.git`, saved server data, authentication material or build/runtime directories. Release binaries must match the verified desktop artifact; documentation must separate network readiness, configuration success and account login. MIT was explicitly selected by the owner.
- Root owns launcher, configuration, integration tests, documentation and packaging.
- Proxy worker owns ProxyTools.ps1 and tests/test_proxy.ps1 only.
- Monitor worker owns remote-monitor.sh and tests/test_remote_monitor.py only.
- SSH import worker owns SshImport.ps1 and tests/test_ssh_import.ps1 only; root owns its launcher integration and manual-query help.
- EXE worker owns exe/Program.cs, exe/Build-Exe.ps1 and exe/app.manifest; EXE test worker owns tests/test_exe.py. Root owns release packaging and documentation. Embedded resources use an explicit allowlist; personal settings and secrets must never be embedded.
- Reviewers are read-only unless root assigns a specific repair.
- GUI UI worker owns gui/GuiApp.cs, gui/Build-Gui.ps1, gui/app.manifest and gui/design.md. GUI backend worker owns gui/TunnelBackend.cs, gui/Gui-Api.ps1 and tests/test_gui_api.ps1. Reviewer owns only tests/test_gui_backend.ps1 for deterministic lifecycle fixtures. Root owns status-protocol integration, tests/test_gui_status.ps1, docs, visual acceptance and release packaging.
- GUI runtime uses WPF/.NET Framework 4.8 with an explicit resource allowlist; keep console release separate. Only a verified remote HTTPS result may appear as ready. Stale monitor evidence must expire. Password prompts remain inside the owned visible SSH console; only fixed monitor status enters GUI logs.
- Windows PowerShell 5.1 is the baseline. Windows runtime uses no Python/Node dependency. The optional v2.4 remote VS Code setup uses the existing remote VS Code Server Node runtime; it must not download dependencies.
- v2.3 native SSH: keep manual and native validation separate; native endpoints are display data, while original alias/config/client references drive actual SSH. Preserve authentication and host-key options, isolate inherited session/forwarding effects, and never execute Match exec during discovery. GUI owns preview as well as connection snapshot directories and cleans them only after child jobs exit. Prefer VS Code's explicitly configured client; never hardcode a personal host to fix a portability issue.
- Never inspect or copy authentication contents. Do not edit local Codex or global SSH configuration. Do not include real server profiles or runtime state in the portable ZIP.
- All network tests are bounded, unauthenticated probes; user login remains interactive inside the visible SSH console.
- v2.2 server catalog: backend worker owns gui/ServerCatalog.cs, gui/TunnelBackend.cs, gui/Gui-Api.ps1 and tests/test_server_catalog.ps1; UI worker owns gui/GuiApp.cs and gui/ServerEditorWindow.cs. Root owns build/manifest, docs, artifact verification and packaging. Reviewer is read-only. Persist manually entered hosts only in the app-owned servers.json; never edit discovered SSH or VS Code settings. Missing SSH configuration must not prevent manual server use. Preserve malformed catalog contents instead of resetting them.
- v2.4 scope supersedes the earlier blanket prohibition on remote VS Code edits: explicit one-click setup may update only the selected remote account's two proxy keys in VS Code Machine settings, with backups and JSONC preservation. Never write local VS Code settings, shell startup files or Codex configuration. Normal tunnel startup remains read-only remotely. Separate setup and tunnel process ownership; cancellation or configuration errors must not stop an active tunnel. Remote patcher worker owns remote-vscode-config.js/.sh and their tests, backend worker owns launch/action integration, GUI worker owns GuiApp.cs/ServerEditorWindow.cs, root owns docs, packaging and independent verification.
